1. Project Overview & Motivation (What & Why?)

Project Title: Secure Cloud-Based File Storage and Document Management System (CloudVault).
Core Concept: A full-stack, self-hosted, privacy-focused alternative to proprietary cloud storage platforms like Google Drive and Dropbox. It provides enterprise-grade authentication, hierarchical folder management, cryptographic link sharing with expiration dates, real-time audit activity logging, and in-browser preview without forced downloads.

The Real-World Problem We Are Solving:

  • Privacy & Vendor Lock-In: Commercial cloud providers scan personal documents, enforce proprietary storage formats, and log sensitive user habits.
  • Security Risks: Weak session cookies and unauthenticated public file URLs lead to data leakage and unauthorized access.
  • Resource Constraints: Small enterprises and academic labs need a secure, lightweight document management solution that respects user-level quotas and maintains strict audit compliance.

Our Proposed Solution:

  • Zero-Trust Authentication: Stateless JWT (JSON Web Tokens) with BCrypt password hashing.
  • Role-Based Access Control (RBAC): Clear permission boundaries (Owner, Editor, Viewer).
  • True In-Browser Previews: Instant viewing of PDFs, PNG/JPEG images, text/code, and media without forcing file downloads to the user's hard drive.
  • Persistent Cloud Architecture: Zero-cost deployment on Vercel (React Frontend), Render (Spring Boot Docker Backend), and Supabase (PostgreSQL Database).

The Life of a File Upload Request (Explain This in Viva!):

1
User selects file in React: Drag-and-drop or file picker passes File object to uploadFile() in DriveContext.jsx.
2
Axios sends Multipart Request: Axios attaches Authorization: Bearer <JWT> and posts to /api/files/upload?folderId=X.
3
Auth Filter Interception: AuthTokenFilter extracts JWT, validates signature with HMAC-SHA256, and populates SecurityContextHolder.
4
FileController & Storage Service: Validates file size (max 50MB) and checks if usedStorage + file.size > storageQuota. If exceeded, rejects with 400 Bad Request.
5
Persistence: Saves metadata to table files, stores binary content into table file_contents (as bytea), updates user's usedStorage, and records an UPLOAD event in activity_logs.

6. Core Theoretical Concepts Used (Must-Know for Professor)

1. JWT (JSON Web Token) Architecture:

JWT is an open standard (RFC 7519) for securely transmitting information between parties as a JSON object. It contains 3 parts separated by dots: Header.Payload.Signature:

  • Header: Specifies algorithm (e.g., {"alg": "HS256", "typ": "JWT"}).
  • Payload: Contains claims (user email, user ID, issued-at time, expiration time).
  • Signature: HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secretKey). Ensures the token cannot be tampered with.
  • Why Stateless? The server doesn't store session IDs in memory or database. Every request is self-verifying, allowing horizontal server scaling.

2. BCrypt Password Hashing & Salt:

Standard hashing algorithms (MD5, SHA-256) are fast and vulnerable to hardware-accelerated dictionary and rainbow table attacks. BCrypt is an adaptive hash function based on the Blowfish cipher:

  • Salting: Appends a random 16-byte string to the password before hashing. Guarantees two identical passwords generate completely different hashes.
  • Work Factor (Cost): In our project, work factor = 10 (210 = 1024 iterations). It intentionally slows down verification to make brute-force attacks computationally infeasible.

3. In-Browser Document Preview (How does it work without download?):

When you click "Download", the server sends header Content-Disposition: attachment; filename="report.pdf". When you click "Preview", the server sends header Content-Disposition: inline; filename="report.pdf" with Content-Type: application/pdf. The browser's native PDF rendering engine / image decoder displays the raw binary stream directly inside our modal iframe without saving it to disk.

4. ACID Properties in our Database:

  • Atomicity: If user uploads a file, saving metadata + saving binary data + updating user storage quota happens in a single @Transactional boundary. If anything fails, everything rolls back.
  • Consistency: Foreign keys prevent orphan files (a file cannot point to a non-existent owner).
  • Isolation: HikariCP pool handles concurrent uploads without dirty reads.
  • Durability: Once committed in Supabase PostgreSQL, data is permanently written to disk.

7. Anticipated Professor Questions & High-Scoring Answers

Q1: Why did you choose Spring Boot instead of Node.js / Express or Django?
"Spring Boot provides enterprise-grade robustness, built-in dependency injection, and declarative transaction management (@Transactional) which is critical when synchronizing database records with binary file storage. Java 17 offers strong type-safety, high concurrency, and Spring Security provides out-of-the-box protection against CSRF, session fixation, and brute-force vulnerabilities compared to manually wiring security middleware in Express."
Q2: Where are the uploaded files physically stored? What happens if Render restarts?
"In local development, files can be stored on the local disk (./storage_uploads). However, because cloud container platforms like Render Free Tier use ephemeral filesystems (disks are wiped on container reboot), we engineered a Database-backed binary storage strategy for cloud production. File bytes are stored directly in PostgreSQL using a dedicated file_contents table with a BYTEA column. This guarantees 100% data persistence across container sleep cycles and reboots at zero cost!"
Q3: How do you prevent Insecure Direct Object References (IDOR) so User A cannot see User B's files?
"Every file access endpoint (download, preview, rename, delete) fetches the authenticated user's email directly from the Spring Security SecurityContextHolder (extracted from the cryptographically signed JWT). Repository queries use composite lookups like findByIdAndOwnerAndIsDeletedFalse(id, authenticatedUser). Even if User A changes the URL ID to User B's file ID, the query returns empty, resulting in an automatic 404 Not Found or 403 Forbidden."
Q4: How does hierarchical folder organization work in SQL? Isn't SQL relational and folders hierarchical?
"We use an Adjacency List Model. The folders table has a self-referencing foreign key column parent_id pointing to folders(id). Root folders have parent_id = NULL. To render breadcrumbs, we recursively traverse up the parent pointers. To list folder contents, we query WHERE parent_id = :folderId. This gives infinite nesting with simple relational queries."
Q5: How does public link sharing work without compromising authentication?
"When a user shares a file, we generate a cryptographically random 32-character UUID token, configure permissions (VIEWER or EDITOR), and set an optional expires_at timestamp in the share_links table. In SecurityConfig.java, the endpoint /api/share/** is permitted publicly. When a recipient accesses /api/share/{token}, the server checks if the link exists and whether now() < expires_at. If valid, it returns only that specific resource stream without giving access to the owner's full drive."
Q6: What is the difference between soft delete and hard delete in your system?
"Soft delete sets the flag is_deleted = true on the file or folder and immediately deducts the file size from the user's active storage quota, moving it to the Trash view. The user can click 'Restore' to flip the flag back to false. Hard delete (permanent purge) deletes the record from both the database and binary table, permanently freeing disk space."
Q7: What is CORS and why did you configure it?
"CORS (Cross-Origin Resource Sharing) is a browser security mechanism that blocks a frontend running on one domain (e.g., https://your-app.vercel.app) from making AJAX requests to a backend on another domain (e.g., https://your-api.onrender.com). We configured CorsConfigurationSource in Spring Security to explicitly permit requests from our frontend domain and expose headers like Content-Disposition so file download names are readable by Axios."
Q8: How do you handle file upload limits and quota enforcement?
"We enforce two layers of validation: first, Spring Boot's MultipartFile configuration sets a hard ceiling of 50MB per file and 100MB per request. Second, at the business logic level in FileStorageService, we verify if user.getUsedStorage() + file.getSize() > user.getStorageQuota() (default 500MB). If exceeded, it throws an IllegalStateException with an informative message before any bytes are written."
